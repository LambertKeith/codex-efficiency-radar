## 问题清单

### 🟡 建议修改

#### 1. 增加统一的 Doctor / Status / Repair

- 证据：兼容检查只能通过选择器内部 `launcher.mjs --diagnose` 触发，README 与根目录没有独立诊断入口。
- 风险：隐藏常驻进程、启动项、端口、插件缓存、兼容白名单或数据源任一环节失败时，用户只能翻日志猜原因。
- 合理范围：增加 `Doctor.cmd`、`Doctor.sh` 和 `scripts/doctor.mjs`；检查 Codex CLI、插件安装版本、启动项、常驻进程、端口占用、当前 Codex 兼容性、数据源连通性和最近错误。支持人类可读输出与 `--json`，`--repair` 只重建本项目管理的状态。
- 验收：一个命令能够明确回答“是否安装、为何没显示、是否需要更新、能否安全修复”。

#### 2. 增加安全更新与回退闭环

- 证据：README 只有 `git pull --ff-only` 后重装；仓库当前没有 Git tag、Release、CHANGELOG 或 `Update.cmd/.sh`。版本 `0.2.0` 分散在根包、插件包、manifest 和 MCP server 中，发布检查只校验名称，没有校验版本一致性。
- 风险：陌生用户不知道何时需要更新；Codex 更新导致白名单失效时只会看到功能消失；升级失败也无法回到上一个可用运行时。
- 合理范围：增加 `Update.cmd/.sh`；先做兼容与版本检查，备份上一版运行时，成功后切换，失败自动回滚。发布使用 SemVer tag、CHANGELOG 和 GitHub Release，并让版本由单一来源生成/校验。
- 验收：更新前后版本可见；失败不破坏上一版；能够一键回退最近一个成功版本。

#### 3. 完成断网/上游故障的降级与退避

- 证据：`RadarClient.lastSuccess` 只保存在内存；冷启动请求失败时无可用快照。`resident.mjs` 等待注入器退出后立即继续循环，没有根据退出码做指数退避。
- 风险：冷启动断网时分数完全不可用；上游持续失败可能导致注入器快速重启、重复请求和日志膨胀。
- 合理范围：保存一个带 schema/version/TTL 的 last-known-good 快照；启动失败时显示“离线旧数据”；守护进程采用有上限的指数退避和抖动，恢复成功后清零。
- 验收：断网冷启动仍可显示明确标记的旧数据；连续失败不会形成热循环；网络恢复后自动更新。

#### 4. 增加有界日志与支持包导出

- 证据：`resident.log` 和 launchd 日志持续追加，没有大小上限、轮转或保留期限；README 也没有日志位置和收集方式。
- 风险：长期运行会无限占用磁盘；用户反馈问题时缺少一致、可脱敏的证据。
- 合理范围：单文件 2–5 MB、保留 3–5 份；Doctor 提供 `--export-support-bundle`，导出版本、兼容结果、启动状态和最近日志，默认去除用户名及绝对路径。
- 验收：日志空间有明确上限；支持包不包含对话、令牌或个人目录信息。

#### 5. 补齐安装/升级/卸载的事务性和幂等性

- 证据：根安装器先变更 marketplace 和插件，再安装选择器；后续非白名单错误之外的异常不会恢复前态。macOS 安装器先停止旧 Agent 并删除旧运行时，失败时只清理新状态，不恢复上一版。
- 风险：安装到一半失败会留下“插件已装但增强损坏”或“旧版本已删除、新版本没装好”的部分状态。
- 合理范围：安装前记录状态；在临时目录完成校验；原子切换运行时；失败时恢复 marketplace、插件和上一版启动项。重复执行安装/卸载应返回成功并保持同一结果。
- 验收：在每个阶段注入失败后，系统要么保持旧版可用，要么恢复到完全未安装状态。

#### 6. 增加跨平台生命周期集成测试

- 证据：现有 12 项测试覆盖 MCP、数据转换、DOM 注入和兼容匹配；CI 没有模拟 Codex CLI、安装目录、Windows 启动项、macOS LaunchAgent、升级失败和卸载残留。
- 风险：最容易影响真实用户的安装与守护链路仍主要靠人工验证。
- 合理范围：为安装器提供可注入的 home/runtime/codex 路径；用 fake Codex CLI 和临时目录验证 install → update → repair → uninstall；对 CDP 做最小协议 smoke test。
- 验收：三平台 CI 可验证幂等安装、回滚、启动项内容、进程匹配边界和无残留卸载。

### 🟢 可选优化

- 在 Doctor 中提供少量高级配置：Codex app 路径、调试端口、日志级别；不建议为此单独建设大型设置界面。
- 增加 Dependabot/Renovate 与定期依赖审计；当前生产依赖审计没有已知漏洞，因此优先级低于上述六项。
- 增加 CONTRIBUTING 和 Issue 模板，适合开源协作，但不属于运行所必需的核心能力。

## 不建议现阶段扩张的方向

- 不建议建设账号、云同步、遥测平台、远程控制后台或独立更新服务，规模明显超出当前插件。
- 不建议把图标、动画、多语言等细节排在维护闭环之前；它们不是当前主要风险。
- 不建议自动绕过兼容白名单；客户端更新后保持关闭是正确的安全策略，应通过 Doctor 和更新提示改善体验。

## 结论

- 结论：`Approved`（现有功能可公开试用），但距离“可长期自助维护的稳定插件”仍有六项基础能力差距。
